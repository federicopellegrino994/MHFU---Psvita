# Pocket Probe 0.4: self-authored Allegrex AOT fixture

0.4 replaces native test callbacks with C++ generated by the actual project
analysis/emitter from self-authored MIPS/Allegrex instructions. These are raw
instruction arrays in make_fixture.cpp, not a PSP SDK-built ELF or the game.
Worker A saves its return address on the guest stack, calls an import stub for
sceKernelDelayThread(2000), resumes, restores the stack and returns 7. Worker B
returns 9 while A waits. A single test-only import handler bridges the delay to
the real Kernel. This is NOT the full HLE registration/lookup implementation.
The Runtime is still a reduced test host; the game runtime is not connected.
Generated output lives only in the build tree. No game code/assets are included.

Build the host first using the commands below. For Vita configuration append:
-DPOCKET_FIXTURE_GENERATOR=/absolute/path/to/build/probe-host/pocket-fixture-generator
Use .exe on Windows. This is a HOST tool; do not cross-compile the generator.
The generator source and the upstream recompiler sources are included. Generated
fixture code is regenerated for each target and is intentionally not committed.

Current test line:
PASS: recompiled Allegrex + delay import + PSP Kernel

Vita execution of 0.4 is pending. Version 0.3's scheduler-only test passed on
the user's Vita, as confirmed by their screenshot. The older sections below
record how the prior diagnostic milestones work and their limitations.

# Pocket Probe 0.3: real Kernel in a reduced test host

Version 0.3 links the upstream `kernel.cpp` and `sysmem.cpp` with the Vita
SceFiber adapter. A TEST-ONLY implementation of Runtime dispatches two native
callbacks. It checks thread creation, strict priority, delay/blocking, another
thread running during that delay, resumption, and thread return statuses.
It does not execute recompiled PSP instructions, register ThreadMan HLE imports,
or link the full runtime.cpp/media/network/graphics stack. The test host must
never be linked into a game executable. This is scheduler integration validation,
not confirmation that a PSP program or the game boots. Device testing is pending.

# Pocket Probe 0.2: Vita fibers bring-up

0.2 adds a `__vita__` SceFiber implementation of the upstream Fiber interface.
The standalone probe now links that implementation and checks 129 cooperative
cycles from the host to worker A, worker B and back to the host. It checks
execution ordering and stack-local integer/double values across resumptions.
The same check runs against ucontext on the development PC. It does not test
the complete PSP scheduler, concurrency, or the game's own threads. Entries
follow the existing Fiber contract and never return. Fibers must be created,
switched and destroyed on their owning host thread, after returning to it.
Vita SceFiber runtime behavior still requires a device test of this build.

This is an experimental starting point for evaluating a native Vita port of the
MHForever runtime, compatible with the player's own copy of Monster Hunter
Freedom Unite. **It does not run the game.** It is an ARM-native diagnostic,
not a PSP/Adrenaline application. No game data or generated game code is included.

Upstream base: https://github.com/Mango77x/MHForever
at `b5cf14184ce6c77288d37131c34d88b07faba919`.
All new code is GPL-3.0-or-later, under the repository's LICENSE.

## What exists

- A separate CMake entry point; desktop builds are unaffected.
- Native Vita framebuffer text at 960x544, input display, repeat and exit controls.
- Upstream PSP memory implementation compiled for ARM32. Checks 32 MiB RAM,
  2 MiB VRAM, cached/uncached aliases, VRAM mirrors, an out-of-bounds read and
  an Allegrex context FPU bit conversion. This is not comprehensive CPU validation.
- The actual upstream ISO9660 and PARAM.SFO readers compiled for Vita.
- Read-only disc structure recognition for the three upstream v1.01 region IDs.
  Recognition does not verify executable hashes or prove the game works.
- A host CLI exercising the same memory and disc inspection code.

The framebuffer is a diagnostic screen, not a game renderer. No 60 fps game
logic, interpolation, HD textures, audio, gameplay or multiplayer is implemented.
The 96 MiB C heap is a diagnostic allocation choice, not the final port's budget.

## Device test

1. Install `pocket-probe.vpk` on a homebrew-enabled Vita using VitaShell.
2. It can be started without any ISO: core checks should pass and the disc check
   should report that the image cannot be opened.
3. Optionally copy your own uncompressed UMD image to
   `ux0:data/pocketprobe/game.iso` and restart the app.
4. TRIANGLE repeats inspection. START + SELECT exits.
5. Return `ux0:data/pocketprobe/probe.log`, plus the Vita model, firmware and
   modification used. If it crashes before a log is created, report that stage.

It never changes the ISO or reads/writes your existing saves. It writes only
its own `probe.log`, replacing the previous report. There is no network access.
Device execution has not yet been verified: cross-compilation alone cannot
establish that the display, file reader and heap operate correctly on hardware.

## Build

With a standard VitaSDK installation (tested with GCC 15.2.0):

```sh
export VITASDK=/path/to/vitasdk
export PATH="$VITASDK/bin:$PATH"
cmake -S vita -B build/probe-vita -DCMAKE_BUILD_TYPE=Release
cmake --build build/probe-vita -j2
```

Output: `build/probe-vita/pocket-probe.vpk`.
No FFmpeg, SDL, game ISO or game executable is needed for this milestone.

For the same checks on the development PC:

```sh
cmake -S vita -B build/probe-host -DPOCKET_HOST=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build/probe-host -j2
python3 vita/test_probe.py build/probe-host/pocket-probe
build/probe-host/pocket-probe /path/to/your/game.iso
```

The automated tests generate tiny synthetic disc fixtures in a temporary folder.
They contain identification strings and dummy bytes only, not original game data.

## Next milestones and acceptance criteria

1. **Hardware baseline**: diagnostic boots; memory checks pass; controls respond;
   device can read the player's ISO; log can be retrieved.
2. **Runtime portability**: replace the desktop fiber implementation with a Vita
   scheduler-compatible implementation; audit C++20, filesystem, atomics, native
   threads, sockets and timing. Run existing self-authored PSP CPU/thread tests
   as recompiled ARM code before using game code.
3. **Game boot**: prepare the exact region executable and overlays on the PC from
   the player's copy; cross-compile generated C++ for ARM32; connect a Vita host,
   read-only disc I/O, controllers and audio. Show progress to the title screen.
4. **GPU backend**: implement the existing `gpu::Backend` interface using Vita's
   GPU, covering texture formats, blending, depth/stencil, transfers and PSP
   framebuffer synchronization. Validate correctness at 480x272 first, then
   evaluate a 960x544 render target. A scaled image alone is not higher-resolution
   rendering. Desktop OpenGL 3.3 shaders cannot simply be reused unchanged.
5. **Gameplay validation**: load a copied save into an isolated test location;
   complete a quest; exercise effects, menus, suspend/resume and repeated loading;
   measure peak RAM and CPU/GPU frame times on real hardware.
6. **Performance**: establish a stable original-rate baseline, then evaluate
   higher resolution and frame presentation. 60 fps simulation and experimental
   interpolated 60 Hz presentation are separate goals. Neither is guaranteed.

Observed blockers in the pinned upstream:

- The original ucontext implementation splits pointers with 32-bit shifts;
  the Vita build now selects SceFiber instead. Hardware validation is pending.
- `platforms/psp/frontend/gl_backend.cpp` is the desktop GPU implementation.
- The root build unconditionally brings in media/network/texture dependencies
  and builds host recompiler tools. Host tools and Vita target libraries need
  separate build graphs.
- The game/runtime use desktop services and C++20 standard-library facilities;
  compiling this small subset does not validate the entire dependency graph.

The next game-specific input is the actual region/version of the player's copy.
The project is a feasibility effort until the runtime and a representative quest
have been measured on hardware.
